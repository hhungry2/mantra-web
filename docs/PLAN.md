# Mantra ブラウザ移植プラン

## Context

1995年のMac用アクションRPG「Mantra」(Syzygy Cult製)をブラウザに移植する。

すでにこのセッションで `Music.dat` の解析に成功し、全9曲のMOD音楽をブラウザで再生できるプレイヤーを `music/index.html` として公開済み。その過程で、ゲーム本体の移植に必要な前提条件がほぼ揃った:

- **全 `.dat` ファイルが同一のXOR鍵 `musicman3320` で難読化されている**ことを確認済み(Allegro の `packfile_password`)。復号ロジックは実装・検証済み。
- オープンソース版のC言語ソース(SourceForge `syzygymantra`)が入手可能で、構造体定義・ゲームループ・読み込み順序が判明している。
- ローカルの Windows 版一式(`C:\Users\USER\Downloads\Mantra-Windows\Mantra-Windows\`)に全アセットが揃っている。

**最も重要な確証**: マップデータのバイト数が構造体定義から算出した値と完全に一致した。

```
256画面 × [ 160タイル × 8バイト + 16体の敵 × 64バイト ] = 256 × 2304 = 589,824 バイト
                                                    ↑ MapData の実サイズと完全一致
MapArea = 256 × 2バイト = 512 バイト                  ↑ こちらも完全一致
```

これによりマップ形式の解読はほぼ確定的に可能。移植の最大のリスクは解消されている。

**目標**: 実際に遊べるブラウザ版Mantraを、垂直スライス方式(まず1画面が動く状態を作り、そこから拡張)で段階的に構築する。

## 判明しているゲーム仕様

| 項目 | 値 |
|---|---|
| 画面構成 | 16×10タイル × 32px = 512×320px + ステータスバー24px = **512×344px** |
| ワールド | 16×16 = **256画面**のグリッド |
| フレームレート | 40ms間隔 = **25fps**(固定タイムステップ) |
| 敵の移動AI | 22種類(`randomMovement`, `homing`, `smart`, `gaurdian`, `circular`, `bumpTurn` ほか + ボス8種) |
| アイテム | 250種類(剣・防具・金・メッセージ・特殊など属性フラグ制) |
| 敵テンプレート | 250種類 |
| 効果音 | 8種(44.1kHz PCM) |
| BGM | 9曲(MOD形式・**移植済み**) |
| セーブ | プレイヤー状態 + 画面ごとの敵撃破ビットマスク |

### アセットの所在

| ファイル | 内容 |
|---|---|
| `GameData.dat` | 13個の独自形式バイナリブロブ(下表) |
| `Images.dat` | 静止画6枚(`story` 468×287, `help`, `win`, `lose`, `mantra`ロゴ, `cursor`) — 単純な `[bpp][w][h]+画素` 形式で**解読済み** |
| `Sound.dat` | 効果音8個(SAMP形式・44.1kHz) |
| `Music.dat` | **対応完了** |

`GameData.dat` の内訳: `MapData`(589,824) / `BossData`(208,896 = 64×64画像51枚) / `FontData`(190,448) / `GameSprites`(84,381) / `MapGraphics`(76,614) / `AnimData`(54,246) / `IconData`(48,840) / `ItemData`(21,144) / `TmplData`(4,556) / `TextData`(3,953) / `StoreData`(1,350) / `SystemPalette.act`(768 = 256色RGB) / `MapArea`(512)

## 方針

- **垂直スライス優先**: 早い段階で実際に触って動作確認できる状態を作り、そこにマップ・敵AI・ボス・セーブを足していく。
- **配置**: 専用リポジトリ [`hhungry2/mantra-web`](https://github.com/hhungry2/mantra-web) の直下に配置する。
- **ファイルは個別に分割**(1枚のHTMLに詰め込まない)。ESモジュールで責務ごとに分ける。
- アセットはビルド時にPythonで抽出し、**PNG + JSON**に変換して同梱(実行時に `.dat` を解析しない)。

## 実装フェーズ

### フェーズ0 — アセット抽出ツール(完了)

実装して分かった、当初の想定と違っていた点:

- グラフィックの圧縮は Allegro の RLE ではなく **Macintosh PackBits**(1995年の68k Mac由来)。`unpack_dat.unpackbits()` で復号する。
- `MapGraphics` の `3000+` は**透過マスク**。当たり判定ではない(地上では壁や水と一致するので当たり判定に見えるが、地下の床が全面「不透明」なので破綻する)。通行可否はタイルの `modifiers` が持つ。`assets/tile_masks.png` として書き出してはあるが、エンジンは使っていない。
- 1画面160タイルは**列優先**(`index = x * 10 + y`)で格納されている。行優先で読むとマップが砂嵐になる。抽出時に行優先へ並べ替える。
- `TmplData` は 70バイト × 65体 = 6バイトのID/長さヘッダ + 64バイトの `Enemy`。
- 画面ごとの敵スロットは64バイトの `Enemy` 構造体そのもの。先頭8バイトはMacのハンドル(実行時のポインタ)なので意味はないが、それ以降は全部生きている。

`tools/` にPythonスクリプトを作る。実行は一度きりで、成果物(PNG/JSON)をリポジトリに commit する。

1. **`unpack_dat.py`**: XOR復号 + `propDATE`/`propNAME`/`propORIG` を辿って名前付きオブジェクトを取り出す共通ライブラリ(このセッションで実証済みのロジックを整理したもの)。
2. **パレット + タイル**: `SystemPalette.act`(256色RGB)を読み、`MapGraphics` の32×32タイル(8bitインデックス色)をアトラスPNG化。`MapGraphics` はIDヘッダ付きの梱包形式(`1000+` がタイル画像、`3000+` が透過マスク)なので、マスクをアルファチャンネルに変換する。
3. **マップ**: `MapData` を 256×[160タイル + 16敵] に分解して `map.json` へ。タイルは `modifiers`(通行可/扉/ダメージ/城・地下への接続)と `spriteRef` を保持。
4. **その他データ**: `ItemData`/`TmplData`/`TextData`/`StoreData` を JSON 化。
5. **スプライト/ボス/アイコン/静止画/効果音**: それぞれPNG・WAVに変換。

**検証**: 抽出したタイルアトラスとマップJSONから、Pythonで数画面ぶんを1枚のPNGにレンダリングして目視確認する。ここでマップが絵として成立していれば、形式解読が正しいことの決定的な裏付けになる(エンジンを書く前にこれを必ず通す)。

### フェーズ1 — 垂直スライス(遊べる最小構成)(完了)

「1画面の中でSaricを操作し、剣で敵を倒せる」状態をゴールにする。実装は画面17(世界グリッド (1,1)、川と橋のある画面)で動く。

フェーズ2に持ち越した未解決点:

- **敵テンプレートの残りのフィールド**。移動AIの種類・速度・接触ダメージがどのバイトかは未特定なので、フェーズ1では テンプレート番号の偶奇で `randomMovement`/`homing` を割り当て、速度とダメージをHPから決めている。
- **敵のアニメーション**。スプライト2000番台は2枚組のものと単独のものが混在しており規則が不明なため、敵は静止画で描いている。
- **タイルの `modifier`(23種)**。扉・城・地下への接続や、ダメージ床の意味づけは未解読。JSONにはそのまま入れてある。

- Canvas初期化 + 25fps固定タイムステップのループ(元コードの `rest(40ms)` 相当)
- タイル描画 + ステータスバー(体力・スタミナ・レベル・所持金)
- Saric: 8方向移動・アニメーション・走り(スタミナ消費)・スペースで剣
- タイルの通行判定
- 敵1〜2種類(`randomMovement`, `homing`)+ 接触ダメージ + 剣による撃破
- 効果音(剣・被弾・敵撃破)+ BGM

### 参考: オリジナルのCソース

`include/GameTypes.h` と `src/LoadData.c` に、データ形式を確定させる定義がそのまま入っている。当初は生バイトから推測していたが、以下はソースで裏付け済み:

```c
struct MapItem { char modifiers; short special; short spriteRef; short expansion; };
enum { standable = 1, isDoor = 2, doesDamage = 4, leadsToCastle = 8, leadsToUnderWorld = 16 };
```

- `modifiers` は**1バイト**。その次のバイトは構造体が初期化しないパディングなので、int16 として読むとゴミが下位に乗る。
- 扉の行き先は `special` にビット詰め: 先タイルx=bit4-7 / y=bit0-3 / 画面行=bit8-11 / 画面列=bit12-15。`leadsToUnderWorld` の扉は画面番号 +128(8行ぶん下)。
- 敵は64バイトの `Enemy` 構造体。`movementType` に22種のAI(50以上がボス8種)、`messageID` に看板の文面番号、`deadItem` にドロップ品が入る。
- アイテムは6バイトのヘッダ + 536バイトの `DataFileItem`、店は `Str255` + 商品数 + (アイテム番号, 価格)。

## 検証方法

各フェーズで以下を実施する:

1. `python -m http.server` でローカル配信し、ブラウザツールで実際に操作して確認する(クリック・キー入力・スクリーンショット)。
2. コンソールエラーがないことを確認する。
3. フェーズ0では、抽出結果をPNGにレンダリングして目視確認する(前述)。
4. 各フェーズ完了時にコミットする。プッシュは都度確認を取る。

## 留意点

- **ライセンス**: オリジナルは **GPLv2** で公開されている(SourceForge)。本移植は元のCコードからの派生物にあたるため GPLv2 を継承する。README とソースヘッダにオリジナル作者(Syzygy Cult / Brett Thayer / Ben Birney / Chris O'Neill)のクレジットを明記する。
- **敵構造体のバイト配置**: 64バイト/体という前提はMapDataのサイズ一致から裏付けられているが、個々のフィールドのオフセットは実データで検証しながら詰める(元コードは旧Mac由来でエンディアン変換が入っているため)。
- **`FontData`(190KB)**: 元のビットマップフォントは初期段階では使わず、Web フォント/Canvas のテキスト描画で代用する。見た目の忠実さが必要になった段階で対応する。
- 音楽再生エンジンは `music/index.html` の実装をモジュールとして再利用する(新規に書き直さない)。
